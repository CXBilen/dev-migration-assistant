# v0.2 — Rehydrate: Post-Restore Bootstrap design

**Status:** draft for review · **Date:** 2026-08-28 · **Milestone:** v0.2 "Rehydrate"

## 1. Problem

v0.1 ends at "files restored". A real migration then needs a manual phase the app knows nothing about:
re-authenticate Claude Code, GitHub CLI and Vercel, re-authenticate every MCP server, notice that pnpm or
`corepack` are missing, reinstall plugins whose cache did not travel, and only then run `claude --resume`.
The app already models the seeds of this — `AttentionItem`, the runtime provider's `Remediation` catalogue
("display only in v0.1"), `MachineInfo.tools`, `gh auth status` probing — but nothing acts on them and
nothing verifies that the environment is actually usable.

v0.2 adds a **Post-Restore Bootstrap Engine** that turns "restore completed" into "development environment
ready", with the same security posture as v0.1: **credentials are never captured or migrated**; the backup
only carries _which authentication relationships must be re-established_, and every action that installs,
authenticates or launches something is explicit and user-approved.

```
Restore → Verify restored files → Bootstrap plan (detect · inspect · diff)
        → approved app-hosted actions (repairs)        ┐ loop until
        → terminal-hosted actions (installs, logins)   ┘ READY
        → health check every integration → READY → Open project in Claude Code
```

## 3. Goals and non-goals

**Goals**

1. Post-Restore Bootstrap Engine with the lifecycle detect → inspect → diff → plan → act → verify → READY.
2. Capability snapshot at backup time (tools, versions, install method, MCP inventory, plugins, auth
   relationships — never credentials) and a source → destination diff on the destination.
3. Claude Code rehydration: validate and repair `~/.claude` / `~/.claude.json` state that is safe to
   regenerate; report what is not; detect version drift.
4. MCP inventory with four health states per server: CONFIGURED · INSTALLED · AUTHENTICATED · REACHABLE.
5. Interactive re-auth orchestration: the app opens the exact command in a terminal, verifies afterwards,
   and sequences the next one. The user always consents.
6. GitHub CLI / Vercel CLI / common dev CLI auth checks; node toolchain and Homebrew presence checks.
7. Missing dependencies installable through the same consent flow.
8. A final "Development Environment Ready" verdict and "Open project in Claude Code" (`claude --resume`).
9. Declarative-plus-code **recipes** so community contributors add a tool without touching core.

**Non-goals (unchanged from v0.1's trust model)**

- Migrating any credential, token, Keychain item or OAuth grant. Bypassing OAuth consent.
- Silent installs or silent logins. The app never runs an installer or a login flow without a click on
  that specific action, and never with elevated privileges.
- Rewriting conversation text or unknown settings schemas (ADR-0005 stands).
- Copying plugin caches or machine-bound state verbatim (they are reinstalled / regenerated).
- Windows/Linux, direct transfer, recovery key, compression — later milestones.

## 4. Approaches considered

**A. Inline restore phase.** Add a `BOOTSTRAP` phase inside `DefaultRestoreEngine.execute` between VERIFY
and REPORT. Has everything in scope, but forces consent-gated, interactive, minutes-long work into one job
that has no pause primitive, and cannot run without a restore.

**B. Separate bootstrap job + recipe registry (recommended).** A new `BootstrapEngine` in core with its
own plan → approve → execute cycle (the same two-phase consent precedent as restore), fed by the retained
restore handoff and the destination disk. Tools are described by _recipes_ registered next to providers.
Also runs standalone ("Check this Mac") because the destination probe pass is identical.

**C. Extend `MigrationProvider` with `health()/rehydrate()` hooks.** Keeps one registry but mixes
"migrate state" with "make tools usable" (GitHub CLI and Vercel migrate nothing), needs a new context
type on the contract, and gives community recipes no data-only surface.

Decision: **B**. `MigrationProvider` stays untouched (only the stale `claudeJsonPath` comment is fixed);
recipes may import provider packages for parsers (e.g. `@devmig/provider-claude-code`'s `readClaudeJson`).

## 5. Architecture

                                     engine.ts (plan/execute/recheck/launchSpec), running-claude.ts

apps/desktop/src/renderer            screens/setup/{setup.tsx, ready.tsx}, store, mock API, Home card,

Dependency direction: `model ← shared ← core ← providers ← recipes ← desktop`. Core never imports a
recipe or provider; both are injected through registries in `createCoreServices`.

### 5.1 Search path (F1)

`resolveSearchPath({ homeDir, basePath, fs })` returns an ordered, de-duplicated list of **existing**
directories: `basePath` entries, `/etc/paths` and `/etc/paths.d/*` (what `path_helper` reads), then curated
user locations: `/opt/homebrew/bin`, `/opt/homebrew/sbin`, `/usr/local/bin`, `~/.local/bin`,
`~/.claude/local`, `~/.bun/bin`, `~/.volta/bin`, `~/.cargo/bin`, `~/.yarn/bin`, `~/.fnm/aliases/default/bin`,
`~/.nvm/versions/node/<alias default or highest>/bin`, `~/.local/share/mise/shims`, `~/.asdf/shims`.
No login shell is spawned — a shell would execute the user's rc files and reintroduce a shell string.
The resolved PATH is set on `Environment.env.PATH` in `createAppEnvironment` and `createEnvironment` wraps
`exec` so `env` is always forwarded (fixing `git-info.ts`, `git-ignore.ts` and any future call site).
The list is recorded in the snapshot (`search.paths`) and shown on Diagnostics; it is re-resolved on
every bootstrap plan so an install made in a terminal is picked up.

### 5.2 Exec hygiene (F2, F3)

- `ExecOptions.stdin?: 'ignore' | 'pipe'` (default `'pipe'`, unchanged). Recipes always pass `'ignore'`.
- `ExecResult.timedOut: boolean` so a recipe can distinguish "timed out while printing a login URL"
  (→ UNAUTHENTICATED) from "failed".
- A `ProbeEnv` helper adds `NO_COLOR=1`, `CI=1`, `GH_PROMPT_DISABLED=1`, `GIT_TERMINAL_PROMPT=0`,
  `VERCEL_NON_INTERACTIVE=1` and scrubs `GH_TOKEN`/`GITHUB_TOKEN` when probing gh state.
- Probes never throw through `Exec` (`reject:false`), never copy stdout/stderr into results, attention
  items or progress messages; they return parsed booleans/enums/versions only.
- Every `claude` invocation goes through `claudeArgv(subcommand, …)` which only accepts the enumerated
  subcommands and validated positional names (`assertSafeArg`), and takes a copy of `~/.claude.json` into
  `<claudeConfigDir>/devmig-backups/` first (reusing the exported `backupClaudeJson`).

### 5.3 Capability snapshot (goal 2)

Captured at backup time by `collectCapabilitySnapshot(env, recipes)` next to the existing
`collectMachineInfo` call in `backup-engine.ts`, and written as the new optional `Manifest.capabilities`
(additive → `formatVersion` stays 1; `machine.json`/`MachineInfo` remain for older readers).

```ts
CapabilitySnapshot {
  schemaVersion: 1, capturedAt, role: 'source' | 'destination',
  search: { paths: string[] },
  tools: ToolCapability[]            // { id, label, installed, version, path, installMethod, recipeId }
  integrations: IntegrationRecord[]  // { id, recipeId, kind: 'cli-auth'|'mcp-server'|'plugin'|'connector',
                                     //   name, scope: 'user'|'project'|'plugin'|'claude.ai'|'machine',
                                     //   projectId?, transport?, command?: basename, url?: origin+path,
                                     //   requiresAuth, sourceState: 'signed-in'|'signed-out'|'unknown' }
  plugins: { id, marketplace, version, enabled }[]
  marketplaces: { name, source: { source, repo } }[]
  claude: { version, installMethod, transcriptWriterVersions: string[] }
}
```

What is deliberately **not** in it: env values, headers, args (only the command basename — the classifier
is run over args/url and the record is dropped from the snapshot if it contains a secret-looking token),
emails, org ids, account uuids, hostnames, absolute install paths of plugins (rebuilt on the destination).
Field names avoid `auth*`/`token*`/`credential*` so `redactObject` does not blank them in diagnostics
(`signedIn`, `health`, `verdict`).

`installMethod` is derived from the resolved path: `native` (`~/.local/share/claude/versions`),
`homebrew` (`/opt/homebrew`, `/usr/local/Cellar`), `npm-global`, `corepack` (shim symlink),
`version-manager` (nvm/fnm/volta/mise), `manual`, `unknown`.

### 5.4 Recipe contract (goal 9)

Data part (zod, `@devmig/model`) so community recipes are validated and displayable:

```ts
RecipeManifest {
  id, displayName, category: 'ai-tool'|'cli'|'runtime'|'package-manager'|'vcs',
  executables: { id, label, file, versionArgs: string[] }[],
  install?: { homebrew?: string[]; corepack?: string[]; npm?: string[]; url?: string },
  signIn?: { check: string[]; login: string[]; logout?: string[]; url?: string },
  credentialPaths: string[],   // never captured; fed to the secret classifier and the scan exclusions
  hosts: string[],             // https hosts the app may open for this recipe
}
```

Code part (`@devmig/core` `bootstrap/contract.ts`):

```ts
interface BootstrapRecipe {
  readonly manifest: RecipeManifest
  detect(ctx: RecipeContext): Promise<ToolCapability[]>
  inventory?(ctx: RecipeContext): Promise<IntegrationRecord[]>        // source: relationships to re-establish
  inspect(ctx: InspectContext): Promise<IntegrationHealth[]>          // destination: passive by default
  plan(ctx: PlanContext): Promise<BootstrapAction[]>                  // from diff + health
  repair?(action, ctx: RepairContext): Promise<ActionOutcome>         // app-hosted, ScopedFs-fenced
  recheck(ctx: InspectContext, integrationIds: string[]): Promise<IntegrationHealth[]>
}
RecipeContext  = BaseContext-like { homeDir, claudeConfigDir, claudeJsonPath, env, exec, logger, signal, progress, searchPaths, cache }
InspectContext = RecipeContext & { expected: IntegrationRecord[]; projects: { id, name, path }[]; active: boolean }
PlanContext    = InspectContext & { source?: CapabilitySnapshot; destination: CapabilitySnapshot; diff: CapabilityDiff; health: IntegrationHealth[] }
RepairContext  = RecipeContext & { fs: ScopedFs /* roots: claudeConfigDir, claudeJsonPath, project paths */ }
```

A recipe with no code hooks beyond the manifest gets generic behaviour: `detect` from `executables`,
`inspect` from `signIn.check` exit code, `plan` producing install/login actions from `install`/`signIn`.
`packages/recipes` ships `claude-code`, `github-cli`, `vercel-cli`, `node-toolchain` (node, npm, pnpm,
bun, corepack), `homebrew`, `git`. `docs/recipes/AUTHORING.md` documents adding one.

### 5.5 Health model (goal 4)

```ts
HealthState = 'pass' | 'fail' | 'unknown' | 'not-applicable'
IntegrationHealth {
  integrationId, recipeId, name, scope, projectId?,
  configured: HealthState, installed: HealthState, signedIn: HealthState, reachable: HealthState,
  verdict: 'ready' | 'action-required' | 'unknown' | 'skipped',
  detail?: string, checkedAt, tier: 'passive' | 'active'
}
```

MCP mapping (from F4): CONFIGURED = present in `~/.claude.json` user/project scope, `.mcp.json`, or a
plugin manifest; INSTALLED = stdio command resolvable on the search path / plugin `installPath` exists /
http always `pass`; AUTHENTICATED (`signedIn`) = not listed in `mcp-needs-auth-cache.json` **and** (active
tier) status ≠ "Needs authentication"; REACHABLE = active tier "✔ Connected", else `unknown`. The passive
tier never spawns anything. The active tier (`claude mcp list` per project cwd, `gh auth status`,
`vercel whoami` guarded by the auth-file check) is one consent checkbox on the plan screen — "Run live
checks (may start configured MCP servers and contact GitHub/Vercel)".

CLI mapping: gh → `gh auth status --json hosts` (state `success` for the host); vercel → auth.json exists
with `token` and unexpired `expiresAt`, then `vercel whoami --format json` (parsed `username` presence
only); Claude → `claude auth status` (`loggedIn` only), `claude doctor` ("No installation issues found.").

### 5.6 Bootstrap plan, actions and consent (goals 1, 5, 7)

```ts
BootstrapAction {
  id, recipeId, integrationId?, projectId?,
  kind: 'active-check' | 'repair' | 'install' | 'sign-in' | 'update' | 'reinstall-plugins' | 'launch',
  host: 'app' | 'terminal',        // app: Exec/ScopedFs inside the job; terminal: user watches
  title, detail, argv?: string[], cwd?: string, network: boolean, writes: string[],
  consent: 'required', status: 'pending'|'approved'|'running'|'done'|'failed'|'skipped'|'awaiting-user'
}
BootstrapPlan { id, restorePlanId?, createdAt, source?: CapabilitySnapshot, destination: CapabilitySnapshot,
                diff: CapabilityDiff, health: IntegrationHealth[], actions: BootstrapAction[],
                readiness: { ready: boolean, remaining: number, blocking: string[] }, warnings: string[] }
```

Consent rules:

- Every action is listed with its exact `argv`, `cwd`, whether it uses the network, and which paths it
  writes. Nothing runs until approved; approval is per action, per plan, and is not persisted.
- **App-hosted** actions are read-only probes and ScopedFs-fenced repairs (roots: `claudeConfigDir`,
  `claudeJsonPath`, restored project paths). They run inside the `bootstrap` job sequentially with
  progress items `<integrationId>:<actionId>`.
- **Terminal-hosted** actions (`install`, `sign-in`, `update`, `reinstall-plugins`, `launch`) are launched
  one at a time on click ("Authenticate", "Install", "Continue setup" launches the next pending one). The
  renderer sends only `{ planId, actionId }`; main resolves the argv from the retained plan, writes
  `<userData>/launch/<actionId>.command` (mode 0700, `#!/bin/zsh`, `cd -- '<cwd>'`, `exec '<abs bin>' 'a' 'b'`
  with single-quote escaping done by our code from validated argv, executables restricted to the
  recipe's declared files resolved on the search path) and opens it with `/usr/bin/open -b com.apple.Terminal`.
  Scripts are swept on the next start. While an action is `awaiting-user` the renderer polls
  `bootstrap:recheck` (passive tier, 3 s) until the integration passes or the user marks it skipped.
- **Blocking guard for writes:** repairs under `~/.claude*` and `reinstall-plugins` refuse to run while a
  Claude Code session is alive (`findRunningClaudeSessions` + `claude agents --json`); the plan shows the
  pids and a "Check again" button. (Restore's own preflight stays a warning in v0.2; making it blocking is a
  separate roadmap item.)
- Quit guard: the app refuses to quit while an app-hosted action is running (dialog), and terminal-hosted
  actions are unaffected by quitting.

### 5.7 Claude Code rehydration (goal 3)

The `claude-code` recipe classifies state as the roadmap suggests and acts only on the middle column:

| Portable (restored by v0.1)                                                                   | Rehydratable (regenerated/repaired here)                                                                                                                                                                                               | Non-portable (never touched)                                                                                                             |
| --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| transcripts, memory, `CLAUDE.md`, settings, MCP definitions, `history.jsonl`, plugin manifest | `projects[path]` entries missing for restored paths, plugin `installPath`/`installLocation` home prefixes, `githubRepoPaths` remap, plugin caches (reinstall), `mcp-needs-auth-cache.json`, `session-env/`, `.last-update-result.json` | Keychain, `oauthAccount`/`userID`/`machineID`, `sessions/*.key`, `ide/*.lock`, managed settings, `*Cache`/`cached*` keys, usage counters |

Checks (all passive unless noted): CLI installed + version; `claude doctor` (active-check); signed in
(active-check); `~/.claude.json` parses; every restored project has a `projects[newPath]` entry and an
encoded session directory whose name matches `encodeProjectDirName(newPath)`; `lastSessionId` resolves to a
transcript (→ enables "Open in Claude Code", else falls back to `claude -c`); memory dir present;
`installed_plugins.json` / `known_marketplaces.json` parse and reference this machine's home; each plugin
`installPath` exists; MCP inventory per scope with the four states; stale references reported
(`disabledMcpServers` naming absent plugins; `claudeAiMcpEverConnected` connectors are informational).

Version drift: `source.claude.version` and `transcriptWriterVersions` vs destination `claude --version`.
Destination older than any transcript writer → `update` action (`claude update`, terminal-hosted).
Destination newer → info row "Claude Code 2.x → 2.y, compatible; local state will be regenerated on first
launch". Nothing compares versions in v0.1 today.

Repairs (app-hosted, ScopedFs, backup-first, add-only): rewrite home prefixes in the two plugin JSON files
via `mapPath`; add missing `projects[newPath]` entries from the restored entry set; remap `githubRepoPaths`
values that point into restored projects; delete nothing. Plugin caches are **reinstalled**
(terminal-hosted `claude plugin marketplace add <owner/repo>` + `claude plugin install <id>@<marketplace>`),
then plugin-scope MCP servers are rechecked.

"Open in Claude Code" (`launch`): argv `claude --resume <lastSessionId>` (or `-c`), cwd = project path.
Before the first launch per project the plan surfaces every `hooks.*[].command`, `statusLine.command` and
`apiKeyHelper` found in the restored user/project settings (F7) and asks once.

### 5.8 Diff (goal 2)

`diffCapabilities(source, destination)` is pure and produces rows:
`{ id, label, source: string|null, destination: string|null, verdict: 'same'|'compatible'|'newer'|'older'|'missing'|'sign-in'|'not-captured' }`.
Node compares by major (existing `majorOf`); everything else by presence + semver-ish string. The runtime
provider's `compareMachines` moves to `packages/core/src/capabilities/compare.ts` unchanged (re-exported
from the provider so its tests and restore attention items keep working); `diffCapabilities` builds on
it rather than beside it. The runtime `REMEDIATIONS` catalogue moves with the hoisted `Remediation` type
and is corrected (`nvm` is a shell function → version-manager-aware; `brew install npm` is invalid;
`reinstall-native-deps` gets a `cwd`).

### 5.9 Jobs, IPC, renderer

- `JobKind` += `'bootstrap-plan' | 'bootstrap' | 'bootstrap-recheck'`; `BootstrapPhase` enum
  (`DETECT`, `INSPECT`, `DIFF`, `PLAN`, `REPAIR`, `CHECK`, `READY`) next to `RestorePhase` (which also gains
  the missing `RESTORE_RUNTIME`); `JobResultSchemas` gains the three results.
- Channels: `bootstrap:plan` `{ restorePlanId?: string; projectPaths?: string[]; active: boolean } → { jobId }`,
  `bootstrap:execute` `{ planId; approvedActionIds: string[] } → { jobId }`,
  `bootstrap:launch` `{ planId; actionId } → { launched: true }`,
  `bootstrap:recheck` `{ planId; integrationIds?: string[] } → { jobId }`,
  `bootstrap:skip` `{ planId; actionId } → { ok: true }`.
  `DevMigrationApi.bootstrap` namespace; preload exact-key tests, `isCompleteBridge`, `bridgeKeys` in the
  smoke E2E and the mock API are all extended (the mock is deterministic: a scripted health timeline).
- `RestoreEngine.getPostRestoreContext(planId)` returns `{ manifest, targets, unitStates }` from the
  retained `StoredPlan` (adds one field: executed results). `CoreServices.bootstrap` is the new engine.
- Renderer routes: `/restore/setup` and `/restore/ready` appended to `RESTORE_STEPS`; `/setup` for the
  standalone entry ("Check this Mac" card on Home and a button on Diagnostics). Restore Report's footer
  gains the primary button **Continue to environment setup**; `report-done` stays.
- Setup screen: environment-difference table (hidden in standalone mode), integrations grouped by recipe
  with four status dots and an action button, a consent panel listing approved actions with argv/cwd/
  network/writes, "Run approved actions", "Run live checks", per-action "Authenticate"/"Install"/"Skip",
  "Continue setup" (launches the next terminal-hosted action), "Check again", readiness counter.
- Ready screen: verdict, per-project **Open in Claude Code**, "Show in Finder", "Done".
- Diagnostics: tools table with resolved path and install method, search paths, passive sign-in states.
- `lib/phases.ts` gets `BOOTSTRAP_RUN_PHASES` and the restore list is corrected to what the engine emits.

## 6. Data flow

```
BACKUP   backup-engine ─ collectMachineInfo ─┐
                        ─ collectCapabilitySnapshot(recipes, role:'source') ─→ Manifest.capabilities
RESTORE  restore-engine execute … VERIFY → REPORT (unchanged) ; StoredPlan retains manifest+targets+unit states
SETUP    bootstrap:plan ─→ job: resolveSearchPath → snapshot(role:'destination', cached 60 s)
                              → diff(source?, destination) → recipes.inspect(passive[, active])
                              → recipes.plan → BootstrapPlan (retained in engine, id → plan)
         renderer approves ─→ bootstrap:execute ─→ job: app-hosted actions in order → recheck → result
         renderer clicks   ─→ bootstrap:launch  ─→ main writes .command, opens Terminal, action=awaiting-user
                           ─→ bootstrap:recheck (poll) ─→ passes → next action
         readiness.ready   ─→ /restore/ready ─→ launch 'open-in-claude'
```

## 7. Error handling

- New append-only `ErrorCode`s: `SIGN_IN_REQUIRED`, `USER_DECLINED`, `INSTALL_FAILED`, `MCP_UNREACHABLE`,
  `COMMAND_FAILED`, `CLAUDE_RUNNING` (already reserved; now used by bootstrap repairs), `LAUNCH_FAILED`.
- A failing recipe never fails the plan: its integrations are marked `unknown` with a warning; a failing
  action marks only that action `failed` and the job continues with the next approved one.
- Probes with timeouts map to `unknown`, except recipe-specific interpretations (vercel timed-out +
  auth file missing → `signedIn: fail`).
- Every `MigrationError` from a terminal-hosted action is reported from the recheck, never from the
  launch (the app cannot observe the Terminal window).

## 10. Security fixes found by the audit (in scope, small)

   restored.
